# Press payout ledger — data model (Otis brief, question 3)

**Proposed model (one paragraph).** We reuse the existing `payout_earmarks` table as the vendor ledger rather than inventing a parallel one: every outbound press payment is a `payout_earmarks` row with `sourceKind='vendor_payout'`, `ownerKind='manufacturer'`, `albumId` as the project linkage, and two new audit columns — `created_by_user_id` (the super admin who initiated the payment) and `inbound_refs` (a jsonb array of `manufacturer_payment_steps` ids: the *paid* inbound customer payments for the same album that the transfer draws from). The Stripe transfer id, release timestamp and any transfer error already live on the earmark row (`stripe_transfer_id`, `released_at`, `transfer_error`), so a project's money-in/money-out view is a pair of indexed queries: money in = `manufacturer_payment_steps WHERE album_id=? AND status='paid'` (already recording amount, margin, payment method and Stripe references), money out = `payout_earmarks WHERE album_id=? AND owner_kind='manufacturer'`. Because a *failed* Stripe call must also be auditable per attempt (the earmark only keeps the latest error), a small append-only `vendor_transfer_attempts` table records every attempt — success or failure — with album, manufacturer, amount, status, transfer id / error message, and the acting admin. Onboarding lifecycle needs no new table: it is derived from the existing `payout_accounts` row for `(owner_kind='manufacturer', owner_id)` — no row = not invited, `details_submitted=false` = Invited, not `payouts_enabled` = Onboarding, `payouts_enabled` = Active — plus two columns (`onboarding_email_sent_at`, `onboarding_email_count`) tracking the emailed Stripe Express onboarding link and resends.

## Where things live
- **Money in** — `manufacturer_payment_steps` (existing, Task #2428/#3004): customer card/bank-transfer payments per project step.
- **Money out** — `payout_earmarks` rows (`sourceKind='vendor_payout'`), minted and released immediately by the super-admin Pay Vendor action (`POST /api/admin/albums/:albumId/pay-vendor`), idempotency-keyed `earmark_<id>` so a retry can never double-pay; `sourceRef='manual_<requestId>'` guards double submits.
- **Attempt audit** — `vendor_transfer_attempts` (new, append-only).
- **Onboarding** — `payout_accounts` (existing) + email-tracking columns; status advances off the `account.updated` webhook with a live-retrieve lazy sync while pending (mirrors the publisher payout-status pattern, since the Connect webhook is fragile).
